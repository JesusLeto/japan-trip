# Модель данных

Типы — в [src/types/trip.ts](../src/types/trip.ts) и [src/types/state.ts](../src/types/state.ts).

## TripData

```ts
interface TripData {
  id: string;                     // напр. 'japan-2026' — часть ключа localStorage
  meta: TripMeta;                  // контент Header/Hero/Footer — НЕ хардкодить в компонентах
  cities: Record<string, string>;  // имя города → hex-цвет (маркеры карты, чипы/акценты дней)
  pre: ChecklistData;               // чеклист «До вылета»
  arrival: ChecklistData;           // чеклист «Сразу по прилёту»
  days: TripDay[];                  // маршрут по дням
  hotels?: HotelsSectionData;       // «Где спать»       (/ 04)
  budget?: BudgetSectionData;       // «Бюджет»          (/ 05)
  practical?: PracticalSectionData; // «Практика»        (/ 06)
  skipList?: SkipListSectionData;   // «Куда не ходить»  (/ 07)
}
```

Четыре последних раздела опциональны: соответствующая секция просто не рендерится, если поля нет.

`TripMeta` содержит все трип-специфичные строки для `Header`/`Hero`/`Footer`/сводки маршрута: `kicker`, `routeSummary`, `heroLabel`, `heroTitle`, `heroTitleAccent`, `heroSubtitle` (**массив абзацев**), `heroChips` (пилюли под хиро), `footerNote`, `routeOverviewSummary` (опционально — нужен только когда у дней есть точки на карте). Названия и подзаголовки самих чеклистов («До вылета» / «Сразу по прилёту») и разметка секций (`/ 01`…`/ 08`) — фичевый UI-копирайт, захардкожен в компонентах, а не часть `TripData` (это не меняется между поездками).

## Две грани одного дня

`TripDay` описывает день **сразу двумя способами** — словами и географией. Это не альтернативы и не разные секции: в `/03 Маршрут день за днём` табы дней (`DayStrip`), клик по табу открывает описание выбранного дня (`DayCard`), а **под ним** карту с маршрутом того же дня.

**1. Нарративная часть** — `blocks` и заметки:

```ts
{
  id, label, city, title,
  points: [], legs: [],
  base?: 'ночь в Осаке',              // где ночуете
  keyTag?: 'Ключевое: Dotonbori вечером',
  blocks?: { morning?, day?, evening? },  // связный текст, поддерживает **жирный** и *курсив*
  transitNotes?: ['Кансай аэропорт → Намба · Nankai Airport Express, ~45 мин · ~¥970/чел'],
  foodNote?: '...',
  planBNote?: '...',
  skipNote?: '...',                    // без префикса «Пропустите:» — его добавляет UI
}
```

Рендерится компонентом `DayCard` — блоки Утро/День/Вечер с транзит-чипами и заметками. Разметка `**жирный**`/`*курсив*` парсится в [utils/richText.tsx](../src/utils/richText.tsx).

**2. Картографическая часть** — `points`/`legs`:

```ts
{
  points: [{ name, coords, desc, arr?, dur?, durMin?, city? }],
  legs: [{ tag, line, time, cost, note?, path? }],
}
```

Обязательны только `name`, `coords` и `desc` — этого достаточно, чтобы точка встала на карту. `arr`/`dur`/`durMin` заполняются, когда известны конкретные даты и тайминг; пока их нет, таймлайн нумерует точки по порядку, а из сводки дня выпадает «~N ч на ногах». `points[].city` заполняется только когда точка не в «домашнем» городе дня; `legs[i]` — транспорт между `points[i]` и `points[i+1]`.

**`legs[i].path`** — реальная геометрия переезда: массив координат, по которым идёт поезд/автобус/пешая дорога. Линия рисуется от предыдущей точки через `path` к следующей, поэтому концы дублировать не нужно. Без `path` сегмент остаётся прямой линией — для пеших переходов внутри квартала этого достаточно, а для железной дороги нет: без неё Nankai из аэропорта «летел» бы через залив по диагонали. Каждый сегмент — отдельная полилиния, так что путь можно уточнять по одному переезду за раз.

### Как получить `path` из OpenStreetMap

Не выдумывайте координаты по памяти — берите трассировку из OSM. Порядок такой (так сделан путь Д1):

1. Найти relation маршрута в нужном коридоре:
   ```
   [out:json][timeout:60];
   rel["type"="route"]["route"~"railway|train"](<south>,<west>,<north>,<east>);
   out tags;
   ```
   Запрос к `https://overpass-api.de/api/interpreter` (при `runtime error: ... too busy` — повторить, сервер отвечает не всегда с первого раза). Среди результатов выбрать нужное направление, например `9583744` — `南海空港線 普通 (関西空港 => なんば)`.
2. Забрать геометрию: `rel(<id>);out geom;`
3. Сшить way-члены с `role=""` в одну ломаную (у соседних ways совпадают концы, часть ways идёт в обратную сторону — их надо разворачивать), упростить алгоритмом Дугласа–Пекера. Для Д1: 163 way → 636 точек → 37 точек при допуске ~30 м.
4. Вставить в `legs[i].path` и указать в комментарии id relation и лицензию: данные OSM под ODbL, атрибуция обязательна.

Рендерится `RouteMap` под описанием; когда у дня есть точки, рядом с картой появляется таймлайн `DayPanelDayDetail` (клик по точке центрирует карту).

### Маршрут заполняется по частям

Координаты добавляются день за днём (сейчас заполнен Д1: аэропорт Кансай → отель в Намбе). Приложение рассчитано на это промежуточное состояние:

- `TripData.mapView` (`{ center, zoom }`) задаёт стартовый вид карты, когда точек нет вообще: Leaflet **обязан** получить явный вид, иначе последующие `flyTo*` бросают `"Set map center and zoom first"`.
- Выбран день без координат — карта показывает общий вид поездки, а не пытается вписать пустые bounds; таймлайна сбоку нет, переезды дня видны чипами в описании (`transitNotes`).
- Сводки дня и поездки (`formatDaySummary` / `formatTripSummary` в `utils/dayInfo.ts`) собираются из непустых кусков, поэтому не появляется мусора вроде «~0 ч на ногах» или «транспорт ~¥0».

Чтобы добавить новый день на карту, достаточно дописать `points`/`legs` в `data/trips/japan.ts` — компоненты менять не нужно.

## Как добавить новую поездку

1. Создать `src/data/trips/<slug>.ts`, экспортирующий константу типа `TripData` (по образцу `japan.ts`).
2. В `src/data/index.ts` поменять `activeTrip` на новую константу (либо — для полноценного мультипоездочного режима в будущем — добавить реальный селектор поездок; в MVP это не реализовано, см. дизайн-спеку).
3. Ничего в `components/`, `state/`, `storage/` менять не нужно — вся адаптация идёт через `TripData`.

## PersistedState

```ts
interface PersistedState {
  checked: Record<string, boolean>;               // itemId → отмечен ли
  custom: Record<string, { id; label }[]>;          // catId → пользовательские пункты
  modes: { pre: 'brief'|'detail'; arrival: ... };    // режим отображения чеклиста
  hideDone: { pre: boolean; arrival: boolean };      // скрывать выполненные
  day: string | null;                                // выбранный день на карте (null = весь маршрут)
}
```

Хранится целиком под ключом `travel-planner:${trip.id}` через `StorageAdapter` (см. [ARCHITECTURE.md](ARCHITECTURE.md)). `normalizePersistedState` в `types/state.ts` добивает недостающие ключи дефолтами при чтении битого/устаревшего JSON.

## Как редактировать существующий маршрут/чеклист

Правьте напрямую `src/data/trips/japan.ts` — это единственная константа, содержащая весь контент (чеклисты, дни, отели, бюджет, практика, skip-лист). Стартовые пункты чеклистов удалить из UI нельзя (`canDelete` вычисляется по признаку «пришёл из `custom`», не из статических данных) — это осознанное ограничение дизайна, не баг.
